## 1. エグゼクティブサマリー

### 1.1 分かったこと【事実】

1. **`eventDate` は元々「注目の日」として設計されていた。** リポジトリに残る最後の記事化プロンプト（2026-07 に外部へ移管）は、`eventDate` を「イベント・試合・オープン・閉店・式典など、カレンダーに『注目の日』として表示したい日付」と定義し、複数日は `eventDates` に書くよう指示していた。その後、イベントカレンダー（`/events/`）と Event 構造化データが同じ項目を「イベントの開催日」として読むようになったことが、意味の混在の根本原因である
2. 日付データ自体はきれいである。`date` は全741件がタイムゾーン付き、`eventDate`（374件）と `eventDates`（92件）に**実在しない日付・逆順の期間・不正な区切りは0件**。問題は値の形式ではなく「意味」と「読み手（テンプレート）ごとの解釈の違い」
3. `eventDate` を持つ ja 記事 362 本のうちイベントは 138 本。残り 224 本（スポーツ 74・開店・閉店 64・グルメ・カフェ 31・お知らせ 30・子育て・教育 21・ニュース 4）もカレンダーと Event 構造化データに載る。開催予定 70 行のうちイベントは 33 行
4. `eventDates`（92本）は**イベントカレンダーにも構造化データにも載らない**。中身は「連続した日の列挙」44・「飛び飛びの日」40・「1日だけ」2・「期間（`A/B`）の列挙」6
5. Event 構造化データは 374 ページ。主催者・会場の 373 件が既定値「浦安市」、番地なし、時刻なし。**日本では Google の Event リッチリザルト自体が提供されていない**（2026-10-05 確認）
6. 開店・閉店年表は、「〜オープン予定」（公式発表の予定）や「出店予定か　求人で判明」（未確定）など、記事の時点で開店していない店舗の記事 31 本をオープン扱いにしている（キュレーション 18・自動分類 13）。今年の「オープン 83 件」にもこれらが含まれる。一時休業・営業再開も閉店・リニューアルに混ざる
7. 投稿ツールと CI の検証は `post-rules.js` を共有しているが、`eventDate` の形式は警告止まり、`eventDates` は検査なし。CI は内部リンクを検査しない

### 1.2 提案の骨子【提案】

| 論点 | 推奨 |
|---|---|
| 日付項目 | `eventDate`（連続期間）・`eventDates`（飛び飛び／複数期間）は「行ける日」に限定。種別は新項目 **`eventKind`**（event／match／fair）で表す。イベントでない注目の日は既存の **`notableDate(s)`**、店舗は新項目 **`shopStatus`＋`shopDate`** |
| 既存記事 | **一括書き換えはしない。** `eventKind` が無い記事はカテゴリから推定する（後方互換） |
| 掲載基準 | カレンダーは `eventKind` が event／match（未設定ならイベント・スポーツ・子育て・教育カテゴリ）。fair（期間限定フェア）は別枠か非掲載を運営判断。個別に `calendar: false/true` で上書き可 |
| 複数日程 | 連続する日はまとめて「6月11日(木)〜14日(日)」、飛び飛びは3日まで列挙・4日以上は「初日ほか全N日」。カレンダーは開催日ごとに独立した行 |
| 構造化データ | 根拠のない既定値（主催者・会場「浦安市」）を廃止。会場が分かる event／match だけを出力。飛び飛びは日付ごとに Event |
| 開店・閉店 | `shopStatus` の語彙を open／open_planned／close／close_planned／temp_close／reopen／renewal／move／feature に拡張。未確定情報は `shopUnconfirmed: true`。年間件数は確定した状態だけ |
| 検証 | Hugo を止めうる日付はエラー（新規投稿・値を変えた更新）。意味の不整合は警告。既存記事は known-issues で通常投稿を止めない |
| リンク検査 | CI に Node 版の内部リンク検査を警告として追加＋投稿ツールで本文の内部リンクを公開済みサイトマップと照合＋プロンプトに正規 URL 一覧 |
| 順序 | サイト側が新項目を「受け付けて検証できる」状態を先に出し、その後プロンプト改訂、その後表示・カレンダーの切替 |

## 3. 日付項目の新しい仕様【提案】

### 3.1 役割の定義

| 項目 | 新しい役割 | 形式 |
|---|---|---|
| `date` | 記事の公開日時（変更なし） | `YYYY-MM-DDTHH:MM:SS+09:00` |
| `lastmod` | 記事の最終更新日（変更なし。CLAUDE.md の運用） | `YYYY-MM-DD` または時刻付き |
| `eventDate` | **読者が「行ける」催し・試合・フェアの、単日または連続した開催期間** | `"YYYY-MM-DD"` または `"YYYY-MM-DD/YYYY-MM-DD"`（配列は使わない） |
| `eventDates` | **飛び飛びの開催日、または複数の会期**（行ける日に限る） | 配列。要素は `"YYYY-MM-DD"` または `"YYYY-MM-DD/YYYY-MM-DD"` |
| `eventKind`（新） | 開催日の種別 | `event`（催し・講座・祭り・展示・見学会）／`match`（試合・大会）／`fair`（期間限定の販売・メニュー・フェア） |
| `notableDate` / `notableDates`（既存・ほぼ未使用） | **イベントではない注目の日**（制度の開始日・告知の対象日・休館日・申込締切など） | `"YYYY-MM-DD"` ／配列 |
| `shopStatus`（新） | 店舗の状態（第7章） | 語彙は第7章 |
| `shopDate`（新） | 店舗の状態が発生する日 | `"YYYY-MM-DD"`、日が未定なら `"YYYY-MM"` |
| `eventEndDate`・`openDate`・`closeDate` | 後方互換として読み続けるが、新規には使わない | — |
| `calendar`（新・任意） | カレンダー掲載の個別上書き | `true` ／ `false` |

「行ける日」の判断: 読者がその日にその場所へ行く・参加する・観戦する・買いに行くことができる日。制度の開始・料金改定・工事・休館・電波発射などは「行ける日」ではないので `notableDate` にする。

### 3.2 「種別」の持たせ方の比較

イベント以外の日付（試合日・開店日・閉店日・告知の対象日）を区別する方法として、2案を比較した。

**A案: 専用項目を分ける**（`matchDate`・`openDate`・`closeDate`・`noticeDate` …）
**B案: 既存の日付に種別を添える**（`eventDate` ＋ `eventKind: match` など）

| 観点 | A案（専用項目） | B案（種別を添える） | 推奨（ハイブリッド） |
|---|---|---|---|
| 1. 既存記事との互換 | 既存の `eventDate` 224本は「意味不明」のまま残る。新旧で項目が分かれる | 既存の `eventDate` をそのまま使い、種別だけ後から足せる | 行ける日は B案、行けない日（告知・店舗）は A案 |
| 2. プロンプトでの出力 | 記事の種類ごとに項目名を選ぶ必要があり誤りやすい | 「日付＋種別1語」で単純 | 「行ける日なら eventDate＋eventKind、そうでなければ notableDate、店舗なら shopStatus」の3分岐 |
| 3. 投稿ツールの検証 | 項目ごとのルールが増える | 種別の値の検査だけ | 種別は列挙値の検査、店舗は状態と日付の組み合わせ検査 |
| 4. Hugo での扱い | カレンダー・構造化データが複数項目を読む | 1項目＋種別の条件で済む | カレンダーは `eventDate(s)` だけ読めばよい |
| 5. 保守性 | 項目が増え続けやすい | 種別の語彙だけ管理 | 項目は既存流用（`notableDate`）＋新項目2つ（`eventKind`・`shopStatus`/`shopDate`） |
| 6. SEO・構造化データ | 試合と催しで Event 出力を分けやすい | 種別で出し分けられる | 種別で出し分け。告知・店舗は Event を出さない |

**推奨はハイブリッド。** 行ける日（催し・試合・フェア）は既存の `eventDate(s)` に `eventKind` を添える。告知の対象日は既存の `notableDate(s)`（サイドバーが既に読んでいる）、店舗は `shopStatus`＋`shopDate` に分ける。こうすると、カレンダーと構造化データは「`eventDate(s)` を持つ記事」だけを見ればよく、`eventDate` を「行ける日」の意味に揃えていける。

### 3.3 未設定の既存記事の扱い（後方互換）

`eventKind` が無い記事は、次の順で推定する（テンプレートの共通 partial で1か所に実装）。

| 1件目のカテゴリ | 推定する種別 | 理由（調査結果） |
|---|---|---|
| イベント | `event` | 予告記事が中心 |
| スポーツ | `match` | 試合日・大会日 |
| 子育て・教育 | `event` | 講座・体験・おはなし会が中心（21本中、制度系は「セカンドブック」等ごく一部） |
| グルメ・カフェ | `fair` | ホテルの季節フェア・期間限定メニューが中心 |
| お知らせ・ニュース・開店・閉店 | **推定しない**（＝注目の日扱い） | 制度開始日・告知の対象日・開店日が中心。イベントは個別に `eventKind` を付ける |

`calendar: true/false` があればそれを優先する（推定の誤りを記事単位で直す手段。移行時に必要な記事だけ付ける）。

### 3.4 形式のルール

- `eventDate` は単日か `開始/終了` の1期間。配列は使わない（既存の配列2本は読み続ける。表示は `eventDates` と同じ扱い）
- `eventDates` は2要素以上。要素は単日または期間。昇順・重複なし。全要素が連続する単日だけの配列（既存 44 本）は、表示では1つの期間にまとめる（`eventDate: "A/B"` と同じ見え方）。新規には `eventDate: "A/B"` を推奨
- `eventDate` と `eventDates` は併用しない（既存1本は同じ日付なので無害）
- 日付は引用符付き文字列（YAML の日付型を避ける。既存の引用なし 4 本は読み続ける）
- 時刻は持たない（時刻を持たせる場合は将来 `eventStartTime` 等を別項目で。今回は対象外）

## 4. イベント掲載基準【提案】

### 4.1 掲載方式の比較

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| ① カテゴリ判定 | 「イベント」カテゴリだけ | 実装が最小・既存データで動く | 試合・子ども向け講座・地域の催し（他カテゴリ）が漏れる。1記事1カテゴリの運用と衝突 |

| ③ 種別判定 | `eventKind` が event／match（／fair）の記事 | 意味で判定でき、構造化データとも共通 | 既存記事には種別が無い |

### 4.2 機能ごとの掲載基準

| 機能 | 対象 |
|---|---|
| `/events/` カレンダー | `eventDate(s)` を持ち、種別（明示または推定）が `event`・`match`。`fair` は運営判断（下記）。`calendar: false` は除外、`calendar: true` は種別に関係なく掲載 |

**fair（期間限定フェア）の扱い**: 開催予定 70 行のうち 17 行がグルメ・カフェ（ホテルの季節ビュッフェ等、最長 2〜3か月）。①カレンダーに含める、②「期間限定」枠として月見出しの外にまとめる、③載せない、の3案。読者の需要はあるが「イベント」とは性質が違うため、**②を推奨**（運営判断）。

**効果の見込み（現時点の開催予定 70 行）**: イベント 33・子育て・教育 7・スポーツ 2 は残る（42 行）。グルメ・カフェ 17 は fair の扱い次第。開店・閉店 5・お知らせ 4・ニュース 1 の計 10 行は外れる（イベントに当たるものは `eventKind` を付ければ戻せる）。`eventDates` だけの今後の記事 16 本のうち、推定で event／match になるもの（イベント 4・スポーツ 5・子育て 2）が新たに載る。

### 4.3 同一イベントの重複との関係

- 種別の整理で減るのは「イベントでない記事の混入」。**同じイベントを扱う複数の記事（予告・続報・結果）が別行で並ぶ問題は解消しない**（工程0 F-2）
- 工程0.5 で「続報は既存記事を更新」の運用を始めたため新規の重複は減る見込み。既存の重複は少数
- イベント ID（例: `eventId`）で記事を束ねる仕組みは**工程5**で扱う。工程1a では、`eventId` を将来追加できるよう項目名を予約するだけとする

## 9. サイト内リンク検査【提案】

### 9.1 事例と現状【事実】

- 2026-10-04 の新記事（防火ポスター展）が存在しない `/life-guide/disaster/` へリンク（PR #9 で修正）。正しい URL は他の記事6本が使っている `/life-guide/disaster-prevention/`。記事化プロンプトが URL を推測で書いたとみられる
- 既存の検査 `scripts/check-internal-links.ps1`: 生成済みの `public/` の HTML から内部リンク（相対・絶対・％エンコード）を全数抽出し、NFC 正規化して実在を確認する。ローカルの手動実行のみ。現在のリンク切れは 0
- CI（`hugo.yml`・`pr-check.yml`）は内部リンクを検査しない

### 9.2 方式の比較

| 方式 | 検出時点 | 精度 | 実装 | 公開への影響 |
|---|---|---|---|---|
| ① プロンプトに正規のガイド URL 一覧を渡す | 生成時（予防） | URL 一覧の更新が必要 | 運営者側 | なし |
| ② 投稿ツールで本文の内部リンクを照合 | 投稿時（即時） | 公開済みサイトマップと照合（新規ページ・転送ページも含めるため `sitemap.xml`＋転送の一覧） | `post-rules.js` に抽出関数、ツールにサイトマップ取得（重複チェックと同じ仕組み） | 警告のみ |
| ③ CI で生成サイトを検査 | push 後 | 最も正確（テンプレート由来のリンクも検出） | 既存 PS スクリプトのロジックを Node に移植して `validate` に統合 | 警告・通知のみ |

**推奨: 3つとも行う。** ①で発生を減らし、②で投稿者がその場で気づけるようにし、③で漏れを確実に拾う。

### 9.3 CI 検査の設計

- 既存の PowerShell スクリプトは GitHub の ubuntu ランナーの `pwsh` でも動く見込みだが、投稿ツールとロジックを共有するため **Node で再実装**する（URL 正規化は `post-rules.js` の `normUrl` を流用。約100行）
- 対象は**サイト内リンクのみ**（`/…` と `https://urayasu-portal.com/…`）。外部リンクはネットワーク依存で不安定なため CI では検査しない（必要なら月1回の手動・定期実行で別途）
- 結果は `validate` の Summary に「リンク切れ（新規）」として出し、`known-issues.json` に既存分を登録できるようにする。公開は止めない
- ビルドは `validate` ジョブ内で既に行っているため、その出力（`$RUNNER_TEMP/validate-public`）に対して実行できる（追加のビルド不要）

## 10. 記事化プロンプトへの反映内容【提案】

### 10.1 整合性の確認結果【事実】

### 10.2 追加・変更する内容

1. 日付の判断フロー
   - 読者がその日に行ける催し・試合・フェア → `eventDate`（単日・連続期間）または `eventDates`（飛び飛び・複数会期）＋ `eventKind`

5. 「〜か」「求人で判明」など未確定の出店情報は `shopStatus: "open_planned"`＋`shopUnconfirmed: true`

## 14. 推奨する最初の実装PR
