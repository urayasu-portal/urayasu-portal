## 1. 結論

1. 年表（`/open-close/`）の対象は「開店・閉店」カテゴリの ja 記事 **120本**（キュレーション61・タイトル自動分類59）。全件を本文（追記を含む）で確認した。**現行の区分と、本文から判断した状態が食い違うのは75本**（キュレーション37・自動38）
2. 現行の「2026年のオープン83件」のうち、**開店済みと確認できるのは28件**。残る55件は、開店予定（40。うち求人などの未確定13）、期間限定出店（9）、リニューアル（4）、閉院（1）、まとめ（1）
3. **「開店予定を開店済みに数えている」記事は42本**（うち未確定13）。閉店も、閉店予定・一時休業を閉店に数えているため 12件 → 6件になる
4. 9種類の `shopStatus` で単一店舗の状態は表せるが、**期間限定出店（ポップアップ）11本**が当てはまらない。10個目の値 `popup` を提案する（第4章）
5. 予定の記事の**34本は予定日を過ぎている**のに、開店・閉店したかが記事に無い。確定した状態だけを数える方針では、これらは更新されるまで件数に入らない。運用（予定日経過の一覧と確認）とセットで導入する必要がある（第7章）
6. タイトル自動分類は、現行の規則で 120本中 **45本**しか推奨と一致しない。判定順の改善で **88本**、さらに「開催日が掲載日より後なら予定」という日付の補助を加えると **100本**まで一致する。それでも20本は合わないため、正規表現は後方互換の最後の手段にとどめる（第9章）
7. 既存記事の件数を正しくするために直す必要がある記事は **45本**（件数に影響43・表示のみ2）。**記事ファイルではなく `data/openclose.yaml` の修正で直す**ことを推奨する（記事を直すと45本の `lastmod` と「更新日」表示が動くため）。PR 5（テンプレート）とデータ修正 PR は分ける（第13章）

## 2. 調査の範囲と方法

- 対象: `content/posts/` の ja 記事のうち、カテゴリに「開店・閉店」を含む120本（年表の120行とURLで全件一致）。あわせて、カテゴリ外でタイトルに店舗の語（オープン・閉店・休業・移転・出店など）を含む22本を確認した
- 取得項目: ファイル名・公開URL（`hugo list all` の permalink）・title・date・categories・eventDate・eventDates・openDate・closeDate・shopStatus・shopDate・shopUnconfirmed・shopName・キュレーションの有無と内容・現行の年表の区分と表示月（main `d62600e2` を本番と同じ条件でビルドした `/open-close/` から取得）・現行のタイトル自動分類
- 判断: 各記事の本文と追記を読み、**記事に書かれている最新の状態**を推奨の `shopStatus` とした。判定日までに予定日を過ぎていても、開店・閉店を確認した記述が無ければ予定のままにし、`plannedPassed` の印を付けた（第7章）。根拠（公式・店舗SNS・店頭掲示・求人・第三者メディア）と確度（確定・予定・未確定・要確認）も記録した
- 一次情報: 本文が引用・要約している一次情報（施設公式・店舗SNS・プレスリリース・求人）を根拠として記録した。外部サイトへの再確認（開店したかどうかの追跡）は行っていない。そのため予定日経過の34本は「未確認」として扱う
- 既存の `shopStatus`・`shopDate`・`shopUnconfirmed` を持つ記事は0本。`openDate`・`shopName` を持つのは1本（マクドナルド新浦安明海店）

### 4.3 9種類で足りるか

**単一店舗の状態は9種類で表せる。**ただし次の3つは、9種類のどれにも自然に入らない。

| 種類 | 本数 | 例 | 提案 |
|---|---:|---|---|
| 期間限定出店（ポップアップ） | 11（ほかにカテゴリ外4） | 「イクスピアリに期間限定5店、9月1日から」「アトレ新浦安に谷中福丸饅頭、10月1日から限定出店」 | **10個目の値 `popup` を追加**（年表に「期間限定」ラベルで表示、件数に数えない）。代替: `feature` に寄せる／年表から外す（第14章 1） |
| 施設全体の開業 | 2 | 「M’av浦安WESTが6月30日開業へ」「…開業 8店舗まとめ」 | `feature`（施設内の各店舗を別記事で数えるため、施設を数えると二重になる）。値の追加は不要 |
| 複数店舗を1記事で扱う | 1 | 「GNOME de TABER・肉じるや5が猫実へ移転」（1店は移転、1店は当面休業） | 記事の主な状態（move）を付ける。値の追加は不要 |

`popup` を値にする理由: イクスピアリ・アトレの期間限定出店は毎月のように記事になる（2026年7〜10月で9本）。常設店の開店と同じ「オープン」に数えると件数が膨らみ（2026年は9件）、読者の「最近この辺にできた店は？」に合わない。`feature` に入れると「まとめ」と表示されて意味がずれる。

### 7.1 方針（第一候補）と実データでの検証

検証で見つかった修正点:

1. **予定日経過（34本）**: open_planned 26本・close_planned 8本が、判定日より前の予定日を持つ。日付つきの公式予定（18本）は、ほぼ予定どおり開店していると考えられるが、記事に確認が無い。確定した状態だけを数える方針では、2026年の開店件数は 28件にとどまる（代替案で数えると45件）
   - 推奨: 予定日を過ぎた予定は、年表で「オープン予定（予定日経過・未確認）」と表示し、件数には数えない。運営側が確認できたものから記事（または yaml）を `open`・`close` に更新する。PR 5 で `planned-passed.tsv` と同じ一覧を CI の Summary に出す（失敗にはしない）
   - 代替: 公式の日付つき予定（未確定でないもの）だけ、予定日を過ぎたら件数に入れる（2026年: 開店45・閉店9）。予定が延期・中止された場合に誤る
2. **renewal に予定の値が無い**: 「アトレ1階が7月9日リニューアル」のように予定として書かれた renewal がある。renewal は `shopDate` が判定日以前のときだけリニューアル件数に数える（日付で判定）。temp_close・reopen・move は件数に入らないので表示だけ
3. **同じ店舗・改装の複数記事（5組13本、`duplicates.tsv`）**: 推奨の区分で数えると、開店は Bambi DROPS（open 2本）、リニューアルはアトレ新浦安の食料品ゾーン改装（renewal 3本）が二重・三重に数えられる。予告と事後の組（GOLF BASE・SUGARY）は予告が open_planned なので二重にならない
   - 推奨: 古い記事を `feature`（または yaml で除外）にするのではなく、**件数は `shopName`（無ければ yaml の `shop`）が同じものを1件に**する。年表の行は記事ごとに残す
4. **タイトルが古いままの記事（3本）**: 「出店予定か　求人で判明」のまま本文で公式確定・開店確認した記事（PAPABUBBLE・OIMO&MOTCH）、「9月下旬オープン予定」のまま開店した記事（田所商店）。タイトルに頼る自動分類では直らない

### 7.2 年表の並びと日付の位置

- 月の見出しは `shopDate` の年月 → yaml の `when` → 公開月の順で決める
- 同じ月の中は、日付まで分かる行を日付の新しい順、その後に年月だけの行（「10月下旬」などの表示は付けず「日付未定」）を並べる
- 日付不明（`shopDate` なし）の行は公開月に置き、「時期不明（掲載月）」と添える
- 現行と比べて表示月が変わる記事は **31本**（遅くなる23・早くなる8）。例: 「#C-pla」9月→10月、「PAPABUBBLE」8月→11月、「石黒産婦人科」8月→7月、「さが美」7月→6月（yaml の `when` が公開月になっていた）

## 9. タイトル自動分類

### 9.1 現行の誤判定

全120本に現行の規則を機械的に当てると、推奨と一致するのは **45本**（キュレーションの無い59本では21本）。キーワード別（現行で外れる本数／その語を含む本数）:

| 語 | 現行で外れる | 改善案で外れる | 含む本数 | 主な原因 |
|---|---:|---:|---:|---|
| 予定 | 30 | 3 | 34 | 「予定」を見ずに open |
| 〜か | 13 | 2 | 15 | 「出店予定か」を open |
| 一時休業 | 2 | 0 | 2 | 「閉店｜休業」で close、または「リニューアル」が先に当たり renewal |
| 臨時休業 | 1 | 0 | 1 | 「再開」が先に当たり renewal（「再開は改めて案内」） |
| 営業再開 | 1 | 0 | 1 | renewal |

| リニューアル | 2 | 0 | 8 | 「一時休業　年内リニューアル予定」を renewal |
| 移転 | 0 | 0 | 2 | — |

### 9.2 改善案（legacy 記事のフォールバック）

上から順に判定する。

1. 一時休業｜臨時休業｜一時閉店｜改装休業｜長期休業｜休館｜休業 → `temp_close`
2. 営業再開｜再開（「再開発」を除く）→ `reopen`
3. 移転 → `move`
4. リニューアル｜改装｜新装｜刷新｜業態転換 → `renewal`
5. 閉店・閉院・閉業・営業終了 の直後に 予定｜へ｜か → `close_planned`
6. 閉店｜閉院｜閉業｜営業終了 → `close`
7. 期間限定｜ポップアップ → `popup`（提案の値）
8. まとめ｜一覧｜閉店していません → `feature`
9. 予定｜見込み｜出店へ｜開業へ｜オープンへ｜〜か｜求人 → `open_planned`
10. それ以外（オープン｜開店｜開業｜開院｜出店…）→ `open`
11. **日付の補助**: 9・10 で open、6 で close になったとき、`eventDate`（`eventDates` の初日）が掲載日より後なら予告記事とみなして `open_planned`／`close_planned` にする

結果（全120本に機械適用）: タイトルだけで **88本**、日付の補助を加えて **100本**が推奨と一致（キュレーションの無い59本では 21 → 52本）。日付の補助で13本が直り、1本（開店後に追記した「鮨やまぐち」）が外れる。

順番による誤判定の確認:

- 1 を 4 より前にしたことで「喫茶さくらが一時休業　年内リニューアル予定」「西友浦安店が一時閉店、夏にトライアル西友へリニューアル」が temp_close になる
- 1 を 2 より前にしたことで「屋久島が臨時休業　再開は改めて案内」が temp_close になる
- 2 の「再開発」除外で「泰興、高架下再開発で移転」が move のまま
- なお残る20本は、タイトルが古い（3本）、業態変更をタイトルが「オープン」と書く（「和麺 善」「DENBAラウンジ」「トライアル西友」）、売場刷新を「再開」と書く（「くりこ庵が再開」は renewal）、期間限定であることがタイトルに無い（「サンリオカフェワゴン」）など、**タイトルだけでは判断できない**もの

### 9.3 優先順位（新仕様）

1. 記事の `shopStatus`（＋`shopDate`・`shopUnconfirmed`）
2. `data/openclose.yaml` のキュレーション（新しい語彙に拡張）

## 11. 記事化プロンプト Stage C への引き継ぎ

PR 5 本番反映後に追加するルール（今回はプロンプト本体を変更しない）:

1. 店舗記事（開店・閉店カテゴリ）は `eventDate`・`eventDates` を使わず、`shopStatus`＋`shopDate` を書く。期間限定出店で `/events/` に載せたい場合だけ、従来どおり `eventDates`＋`eventKind: "fair"`（＋必要なら `calendar: true`）
2. `shopStatus` の選び方:
   - `open`: 開店したことを確認できた（開店日が過去で、公式・店舗・現地で営業を確認）
   - `open_planned`: 開店予定（予定日が未来、または開店を未確認）
   - `close`: 閉店した／`close_planned`: 閉店予定（まだ営業中）
   - `temp_close`: 一時休業・臨時休業・改装休業（再開予定があってもこれ）
   - `reopen`: 休業からの営業再開（改装を伴わない）／`renewal`: 改装・業態変更・売場刷新を伴うリニューアルオープン
   - `move`: 移転（移転先のオープンも含む）
   - `feature`: まとめ・店舗一覧・訂正・施設全体の開業など、単一店舗の状態でないもの
   - `popup`（採用時）: 期間限定出店
3. `shopDate`: その状態が起きる（起きた）日。日まで分かれば `"YYYY-MM-DD"`、月までなら `"YYYY-MM"`。「下旬」「末」「夏」「年内」「◯月〜◯月」は**日付に変換しない**（月だけ分かれば年月、それ以外は書かない）
4. `shopUnconfirmed: true`: 求人・第三者メディアだけ・「〜か」「とみられる」など、公式・店舗・現地で確認できていない情報。確定したら外す。閉店・閉院の未確定情報にも使う
5. 日付不明: `shopDate` を書かない（掲載日を代わりに入れない）
6. 続報の運用: 予定日を過ぎて開店・閉店を確認したら、既存記事の `shopStatus` を `open`・`close` に更新し、`shopDate` を実際の日にする（`lastmod` も更新）。**タイトルの「予定」「〜か」も更新する**
7. `shopName`（任意）: 年表の表示名・同一店舗の件数の重複除去に使う。続報・予告と同じ表記にする
8. 1記事に複数店舗の状態があるときは、主な1店舗の状態を書く（ほかは本文で説明）

## 12. 既存記事の移行方針

- **一括で全記事を書き換えない**。新規記事から `shopStatus`／`shopDate` を使い、テンプレートは legacy 記事を yaml と改善した自動分類で読み続ける（第一候補どおり）
- 実測: PR 5 の新しい読み取り（`shopStatus` → yaml → 改善した自動分類＋日付の補助）でも推奨と合わない記事は **45本**（`fix-candidates.tsv`）
  - キュレーション済み37本（yaml の `type: open` が実際は予定・期間限定・業態変更など）: **すべて件数に影響**
  - キュレーションなし8本: 件数に影響6・表示のみ2
- これらは**記事ファイルを直さず、`data/openclose.yaml` に新しい語彙（`status`・`date`・`unconfirmed`）を足して直す**ことを推奨する
  - 理由1: 記事を直すと CLAUDE.md の規則で `lastmod` を更新することになり、45本の「更新日」表示と sitemap の lastmod が一斉に変わる（内容は変わらないのに「更新」に見える）
  - 理由2: yaml は年表専用のデータで、修正が他の機能（カード・`/daily/`・終了通知）に波及しない
  - 理由3: 1ファイルの差分なので確認しやすい
- 予定日経過の34本は、運営側で開店・閉店を確認できたものから yaml（または続報として記事）を更新する。確認できないものは予定のまま
- **PR を分ける**: ①PR 5 本体（テンプレート・検証・テスト。記事と yaml の内容は変えない）→ ②データ修正 PR（`data/openclose.yaml` の45本＋語彙の移し替え。記事ファイルは変えない）。①だけでも、yaml の無い記事は改善した自動分類で読むため件数は改善する（2026年、yaml の旧 `type` のまま重複除去なしの試算: オープン 83 → 52、閉店 12 → 9、リニューアル 11 → 9。②まで入れると 28・6・9）。①だけの件数は PR 5 の実装後にビルドで確定させる
