## 4. `/events/`（イベントカレンダー）

### 4.1 掲載条件

上から順に判定する。解釈できる開催日（`eventDate`・`eventDates`）が無い記事は、どの場合も載らない。

| 条件 | 掲載 |
|---|---|
| `calendar: false` | 載せない |
| `calendar: true` | 載せる（fair・種別なしも） |
| `eventKind: event`／`match` | 載せる |
| `eventKind` なし＋1件目のカテゴリ「イベント」 | 載せる（従来どおりの推定） |
| それ以外（fair、種別なしのほかのカテゴリ） | 載せない |

- ほかのカテゴリ（スポーツ・グルメ・開店・閉店など）からは推定しない
- `calendar` は種別を書き換えない（`calendar: true` の fair はカレンダーには載るが、種別は fair のまま。Event JSON-LD も出ない）
- `notableDate(s)`・`shopDate` は使わない（`calendar: true` でも開催日が無ければ載らない）
- fair 専用の欄は作っていない

### 4.2 状態と表示

- **状態は全日程で判定する**。未来の日程が1つでも残る間は「終了」にしない（旧版は先頭の `eventDate` だけを見ていた）
  - 今日を含む日程がある → 開催中（日付欄はその期間。複数あれば終了日の近いもの）
  - 無ければ、次の日程がある → 開催予定（日付欄は次の日程）
  - どちらも無い → 終了（過去の一覧へ。全日程の最終日の新しい順に30本、日付欄は初日。旧版は先頭の日付の新しい順）
- `eventOngoing: true`（終了日未定）は、開始前は開催予定、開始日以降は開催中。終了日を推測しない。開始前・開始後とも、日付欄に「〜」、下に「終了日未定」を表示する
- **1記事1行**。日程が2つ以上ある記事は、下に「**今後の日程：**」として、判定日の時点で残っている日程だけを要約する（第4.3節）
- 開催中の並び順は終了日の近い順。終了日未定は開催中の末尾
- match には「試合」の印を付ける（記事カードの「試合日」と同じ色）
- 年をまたぐ終了日は年を付けて表示する（例: `7/24(金)〜2027/3/31(水)`。旧版は `3/31` と年が無かった）

### 4.3 今後の日程の要約（最終調整で追加）

`/events/` はこれから参加できる催しを探すページなので、要約は残っている日程だけで作る。

- 残っている日程 = 終了日が判定日以降の日程（**開催中の会期を含む**。終わった単日・会期は含めない）。連続した単日だけの日程は PR 3 と同じく1つの期間として扱う
- 書式は PR 3 の記事カードと同じ部品を使う
  - 残り1日程 → その日程（例: 「今後の日程：10月17日(土)」）
  - 残り2〜3日程 → 列挙（例: 「今後の日程：2027年1月22日(金)・2月5日(金)」）
  - 残り4日程以上 → 「次回の日程ほか全N日程」（N は残っている日程の数。例: 「今後の日程：10月10日(土)ほか全5日程」）
- 終了日未定（`eventOngoing`）の記事は要約を作らず、「終了日未定」を表示する
- 見出しは、全日程ではないことが分かるよう「日程：」から「今後の日程：」に変えた
- **`/events/` だけの表示**。記事カード・`/daily/`・サイドバー・終了通知・イベント情報ボックスの日付表示（PR 3 の確定仕様）は変えていない（第7章の全数比較で一致を確認）

### 4.4 「今日」の判定（日本時間）

- `layouts/partials/date-jst.html` で、時刻を `time.In "Asia/Tokyo"` で日本時間に変換してから日付を取り出す。タイムゾーンのデータは Hugo に組み込まれていて、ビルドする環境に依存しない
- 旧版の `now.Add 9h` は、ローカル（日本時間の PC）でビルドすると15時以降に翌日扱いになっていた。最初の実装の `now.UTC.Add 9h` も結果は正しいが、「UTC に9時間足す」という暗黙の前提だったため、日本時間を名前で指定する方式に改めた
- テスト専用に `site.Params.eventsNow`（判定する時刻の固定）を読む。本番の設定には置かない
- 固定テスト（`events-hugo.mjs` の後半）: 判定時刻を固定した最小サイトを、環境変数 `TZ` を `UTC`・`Asia/Tokyo`・`America/Los_Angeles`・`Pacific/Kiritimati`（UTC+14）の4通りに変えてビルドし、日本時間の日付と、10/4・10/5・10/6・2027/1/1 の単日イベントの区分（開催中・開催予定・終了）を確かめる

| 判定する時刻 | 日本時間の日付 | 結果 |
|---|---|---|
| 2026-10-04T14:59:59Z（JST 10/4 23:59:59、0時の直前） | 2026-10-04 | 4通りとも一致 |
| 2026-10-04T15:00:01Z（JST 10/5 00:00:01、0時の直後。UTC は 10/4） | 2026-10-05 | 4通りとも一致 |
| 2026-10-05T05:59:00Z（JST 10/5 14:59） | 2026-10-05 | 4通りとも一致 |
| 2026-10-05T06:00:00Z（JST 10/5 15:00。旧実装のローカルビルドで翌日になっていた時刻） | 2026-10-05 | 4通りとも一致 |
| 2026-10-05T14:59:00Z（JST 10/5 23:59） | 2026-10-05 | 4通りとも一致 |
| 2026-10-05T20:00:00Z（JST 10/6 05:00。UTC は 10/5） | 2026-10-06 | 4通りとも一致 |
| 2026-10-05T23:59:00+09:00（+09:00 表記） | 2026-10-05 | 4通りとも一致 |
| 2026-10-05T10:30:00-04:00（JST 10/5 23:30、-04:00 表記） | 2026-10-05 | 4通りとも一致 |
| 2026-12-31T15:00:00Z（JST 2027/1/1 00:00。年の境目） | 2027-01-01 | 4通りとも一致 |

- 15時の判定では、指示書の例（5日程 9/1・9/15・10/10・10/20・11/3）の今後の日程が 10/10・10/20・11/3 になることも確かめる
- Windows 版の Hugo は環境変数 `TZ` を読まないため、ローカルでは4通りが同じ条件になる。GitHub Actions（Linux）では `TZ` が効くので、PR Check で実際に4つのタイムゾーンで確かめられる
- テストが変換漏れを検出することを確かめた（日本時間への変換を外すと、0時直後・UTC と日付が違う時間帯・年の境目の3件が失敗し、終了コード1）

## 5. Event 構造化データ（JSON-LD）

### 5.1 出力条件と内容

| 項目 | 内容 |
|---|---|
| 対象 | posts の記事で、解釈できる開催日があり、種別が event・match（1件目のカテゴリ「イベント」からの推定を含む）で、`eventLocation` が空でない文字列 |
| 使わないもの | `calendar`（カレンダーの掲載とは独立）、本文・タイトル・カテゴリからの会場の推測 |
| 会場 | `location` は `Place` の `name` だけ（`eventLocation` の値）。**住所は出さない** |
| 主催者 | `organizer` が空でない文字列のときだけ。無ければ `organizer` プロパティ自体を出さない |
| 廃止した既定値 | 会場「浦安市」、主催者「浦安市」、住所「浦安市・千葉県」 |
| 日付 | 共通の解釈だけを使う。単日は `startDate` だけ、期間は `startDate`・`endDate`、終了日未定は `startDate` だけ。生の `"開始/終了"` は出さない。解釈できない値は除く |
| 複数日程 | 表示用の日程ごとに1つの Event（最大10件）。同じ日程は1回だけ。`@id` を `記事URL#event-1` のように分ける |
| 料金 | `eventFee` があるときだけ `offers`。`price` は「無料」のときだけ `"0"`（旧版は「500円」などの文字列を `price` に入れていた）。現在 `eventFee` を持つのは花火大会の1本だけ |
| `eventEndDate` | 読まなくした（使っている記事は0本。終了日は `eventDate` の期間で書く） |
| 出力方法 | 文字列の手組みをやめ、`dict` → `jsonify` で生成する（引用符などのエスケープ漏れが起きない） |

### 5.3 今後への影響

- Event JSON-LD は、記事化プロンプトの Stage B で `eventLocation`（と任意で `organizer`）を出力するまで、ほぼ出ない状態になる。誤った会場・住所を出し続けるより安全側を選んだ確定仕様どおり（運営者承認済み）
- 既存記事へ `eventLocation` を後から足せば、その記事から出る（記事修正 PR の対象。本 PR では記事を変更していない）

## 6. `eventLocation`・`organizer` の検証

どちらも任意項目。無いことは警告にしない。未確定のときは「未定」と書かず、項目ごと省略する運用。
