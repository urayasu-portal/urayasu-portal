## 第6章 既存記事の更新との互換性

### 6.1 仕組み

投稿ツールは、更新のとき GitHub API から既存ファイルの全文を取得している（改修前から、URL 衝突の判定に使用）。この全文を `validatePost` に `prevText` として渡し、項目ごとに比較する。

| 状況 | 開催日のエラー |
|---|---|
| 新規投稿 | 適用する |
| 更新で `eventDate`・`eventDates` を追加した | 適用する |
| 更新で値を変更した | 適用する |
| 更新で値を変更していない（本文・`lastmod` だけの続報など） | **警告に下げる**（「既存の値で、今回の更新では変更されていないため投稿は止めません。修正を推奨します」） |
| 既存ファイルの内容を読めない（取得した本文の復号失敗・frontmatter が壊れている） | 変更の有無を判定できないため**新規と同じ基準**で検証し、`EVENT_PREV_UNAVAILABLE` の警告で知らせる。推測で復元しない |

- 比較は解析後の値で行うため、クォートの有無など書き方だけの違いは「変更なし」とみなす
- `date`・`slug`・`title` を自動で変更する処理は無い（改修前と同じ）
- 既存ファイルの取得が 404 以外で失敗した場合、改修前から新規として扱われる。この場合は新規と同じ厳格な検証になり、既存ファイルへの書き込みは sha の指定が無いため GitHub 側で拒否されるので、データは壊れない（挙動は変更していない）
- Hugo のビルドを止める値（第4章）は、本番に存在すればビルドが失敗しているため、「既存の値のまま更新」が起きるのは逆順・3区切り・`eventDates` の不正要素など、ビルドを止めない値に限られる

## 第8章 投稿ツールと PR Check で防げる範囲

| 経路 | 不正な開催日の扱い | 防げるか |
|---|---|---|
| 投稿ツール（日々の記事投稿・続報の全文置換） | 新規・変更した値はブロック | **防げる**（本 PR の主目的） |
| Pull Request 経由の変更（Claude Code 等での修正） | `pr-check` の Validate content が失敗する | **マージ前に検出できる**（失敗した PR をマージしない運用が前提） |
| main への直接コミット（GitHub の Web 編集・ローカルからの push 等） | CI の `validate` は通知のみ。Hugo の `build` が失敗し、デプロイされない | **防げない**。サイトは直前の公開状態のまま残るが、修正するまで以後の記事も公開されない |

- 直接コミットの経路を塞ぐには、`hugo.yml` の `build` に `needs: validate` を付ける方法がある（README に記載済みの選択肢）。ただし、開催日以外の新しい不備でも公開が止まる副作用があるため、運営判断とする（本 PR では変更していない）
- 投稿ツール以外で記事を編集する場合は、PR を作って `pr-check` の結果を確認してからマージすることを推奨する
