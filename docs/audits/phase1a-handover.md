## 1. `eventDate` と `eventDates` の使い分け

### 現状

| 項目 | 記事数 | 書式 | 読んでいる箇所 |
|---|---|---|---|
| `eventDate` | 362（イベント 138・スポーツ 74・開店・閉店 64・グルメ・カフェ 31・お知らせ 30・子育て・教育 21・ニュース 4） | 単日 `YYYY-MM-DD`／期間 `A/B`／配列（2記事） | カードの開催日ラベル（イベントのみ）・`/events/`・Event 構造化データ・終了通知・記事詳細のイベント情報ボックス・サイドバーのカレンダー |
| `eventEndDate` | 0 | 日付 | `/events/`・Event 構造化データ・カード（対応済みだが未使用） |
| `eventDates` | 92（イベント 55・子育て・教育 10・スポーツ 10・グルメ・カフェ 8・開店・閉店 4・お知らせ 3・ニュース 2）。`eventDate` 併用 1 | 日付の配列 | サイドバーのカレンダーの点灯・`/daily/` の「注目の日」だけ |
| `notableDate(s)`・`openDate`・`closeDate` | 少数 | 日付 | サイドバーのカレンダーの点灯 |

- `eventDate` は「開催日」「試合日」「開店・閉店日」「告知の対象日・制度の開始日」を兼ねている（イベント以外が 224 記事）
- 「飛び飛びの日程」が `eventDate` の配列（2記事）と `eventDates`（92記事）の2通りで書かれている

### 決めること

1. 項目の意味の定義（案）
   - `eventDate` … 連続した開催期間（単日 or `開始/終了`）。**イベントのみ**
   - `eventDates` … 飛び飛びの開催日の列挙。**イベントのみ**
   - 試合日・開店日・告知の対象日は別項目（例: `matchDate`、`shopStatus`＋`statusDate`、`noticeDate`）。既存の `notableDate(s)`・`openDate`・`closeDate` との統合も検討
2. 後方互換: 旧記事の一括書き換えはしない。テンプレートは「新項目 → 旧 `eventDate`」の順で読む。旧形式は検証で警告に留める
3. 「イベントかどうか」の判定基準: 1件目のカテゴリ（工程1b のカード）と「どこかにイベント」（終了通知）でずれている。どちらかに統一するか、明示の項目にする

## 2. 飛び飛びの日程を持つイベントの扱い

- **カード**: `eventDate` の配列は「初日＋ほか」。`eventDates` だけのイベント 55 本（例: べか舟の帆づくり 10/25・11/3）は開催日ラベルなし
- **カレンダー・構造化データ**: 配列は初日〜最終日の連続期間として扱われ、「10/25〜11/3」のように誤って見える。`eventDates` だけの記事は載らない
- 推奨: 飛び飛びの日程は `eventDates` に一本化し、カードは 2〜3日なら「10月25日(日)・11月3日(火)」、それ以上は「初日ほか全N日」。カレンダーは日付ごとに1行、構造化データは日付ごとの Event（または `eventSchedule`）。カードの変更は `layouts/partials/card-dates.html` の1か所
- 記事側の個別修正（べか舟の記事など）はしない

## 3. イベントカレンダーの掲載基準

- 現状: `eventDate` があればカテゴリを問わず掲載（イベント以外 224 記事）。`eventDates` だけのイベント 55 本は不掲載。開催前・開催中の件数は 70 行（`a9c986eb` のビルド時点）
- 推奨: イベント（または明示の項目）に限定。スポーツの試合を載せるかは運営判断（載せるなら「試合」の区分で）
- 影響: 掲載件数が大きく変わる。工程5（カレンダー改修）の前提なので、工程1a で基準だけ先に決める
- 「開催中／終了」の判定はビルド時点で固定、境界は JST 9時（工程0 C-1-b・P23）。工程5 で扱う

## 4. Event 構造化データの正確性

- 現状: `eventDate` を持つ全ページで Event を出力 — **374 ページ**（ja イベント 138・スポーツ 74・開店・閉店 64・グルメ・カフェ 31・お知らせ 30・子育て・教育 21・ニュース 4、翻訳版 12）。例: テレビ受信障害のお知らせも Event になり、主催者は既定値の「浦安市」
- 主催者・会場の既定値「浦安市」、`price` への文字列の混入（工程0 P05）
- 推奨: 掲載基準をカレンダーとそろえる（イベント以外は Event を出さない）。主催者・会場は値がある場合だけ出力。飛び飛びの日程は日付ごと。変更後はリッチリザルトテストで数ページ確認
- 工程7a（Event 構造化データ）と重なるため、工程1a では「どのデータから出すか」の定義までを決め、出力の作り込みは 7a でもよい

## 5. 開店・閉店・一時休業・営業再開などの分類

- 現状（`/open-close/`）: 「開店・閉店」117 記事のうち `data/openclose.yaml` でキュレーション済み 58、残り 59 はタイトルの正規表現で自動分類（移転 → リニューアル｜改装｜再開｜新装 → 閉店｜休業 → まとめ → それ以外はオープン）。語彙は open / close / renewal / move / feature の5種
- 自動分類の誤り（`2237f4bf` 時点）
  - 「出店予定か　求人で判明」などの未確定情報 13 本 → **オープン**（年表冒頭の年間オープン件数にも数えられる）
  - 「一時休業」→ 閉店（ブールミッシュ）、「一時休業　年内リニューアル予定」「臨時休業　再開は改めて案内」→ リニューアル
  - 「営業再開」→ リニューアル（ナナズグリーンティー）
- 推奨
  - 語彙を拡張: `open_planned`（出店予定・未確定）／`open`／`temp_close`（一時・臨時休業）／`reopen`（営業再開）／`close`／`renewal`／`move`／`feature`
  - 記事 frontmatter に `shopStatus`（上の語彙）を持たせ、`openclose.yaml` のキュレーションと正規表現は後方互換のフォールバックへ格下げ
  - 年間件数は確定した `open`・`close` だけを数える
  - 正規表現の順序だけを入れ替える修正はしない（「休業から再開」等で別の誤分類が出る）

## 6. 投稿ツールと CI の日付検証

- 現状（`static/tools/post-rules.js`。投稿ツールと CI の `validate-content.mjs` が共有）
  - エラー: `date` の必須・形式・実在、`eventDate(s)` があるのに `hideEventBox: true` が無い
  - 警告: `DATE_NO_TZ`・`DATE_FUTURE`・`DATE_FAR_FUTURE`・`DATE_FILENAME_MISMATCH`・`EVENTDATE_FORMAT`（形式・実在）・`EVENTDATE_EMPTY`
  - 検査していない: 期間の逆順、3区切り以上、`eventDates` の形式、`eventDate` と `eventDates` の併用、イベント以外のカテゴリでの `eventDate`
- リスク: 実在しない `eventDate`（例: 2月30日）は警告で通るが、`/events/` と終了通知の `time` 関数で**ビルドが止まる**
- 推奨: `eventDate`・`eventDates` の形式・実在をエラーに格上げ。逆順・3区切り以上・併用・イベント以外での使用は警告。新項目（1. で決めるもの）のルールとテストを `post-rules.js` と `scripts/validate/test/run-tests.mjs` に追加（工程0.5 の仕組みでツールと CI に同時に効く）

## 7. 記事化プロンプトとの整合性

- 記事化プロンプトはリポジトリ外（運営者側）。posts の frontmatter はプロンプト＋投稿ツールが生成するため、**データ定義の変更はプロンプトの改訂と同時リリースが条件**（工程0 第1章 1.4）
- 工程1a でプロンプトに反映すべき内容
  - 1. の項目定義（`eventDate`／`eventDates`／試合日・開店日等の別項目）と書式
  - 5. の `shopStatus` の語彙と、「出店予定か」など未確定情報の扱い
  - 内部リンクに使ってよい URL の一覧（8. 参照）
  - 工程0.5 からの申し送り: 続報は原則既存記事を更新、別記事にする場合の slug 規則、frontmatter を `---` から始め前置き文を入れない
- 進め方: 運営者がプロンプト改訂案を作る → 投稿ツールの検証ルールを同じ定義で更新 → テンプレートを新旧両対応にする → 同時に反映

## 8. サイト内リンク切れの再発防止

- 事例: 2026-10-04 の新記事（防火ポスター展）が存在しない `/life-guide/disaster/` へリンク（PR #9 で修正）。記事化プロンプトが URL を推測で書いたとみられる
- 現状: 内部リンクの全数検査 `scripts/check-internal-links.ps1` はローカル実行のみ。CI（`hugo.yml` の validate・`pr-check.yml`）は内部リンクを検査しない
- 推奨
  - CI に内部リンク検査を追加（生成済みの `public/` に対して実行。**警告のみで公開は止めない** — 工程0.5 の validate と同じ方針）。PowerShell スクリプトは GitHub の ubuntu ランナーの `pwsh` で動く見込みだが、`validate-content.mjs` 側に Node で実装する方が投稿ツールと共有しやすい
  - 投稿ツールでも、本文中の `/life-guide/`・`/travel-guide/` 等へのリンクが既存ページか照合する（公開済みサイトマップとの照合。重複チェックと同じ仕組みが使える）
  - 記事化プロンプトに、よく使うガイドの正しい URL 一覧を渡す
  - 生活ガイドの URL を変える場合は aliases を必ず付ける（CLAUDE.md の既存ルール）
