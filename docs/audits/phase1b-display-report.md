### 2.3 新しい表示ルール

1. **カードの主たる日付は常に公開日**（frontmatter の `date`）。表示と `datetime` 属性は同じ日付。書式はサイト共通の「2026年10月3日」
2. **開催日ラベル**は、次の3条件をすべて満たすときだけ、公開日の上に別の行で添える
   - 日本語ページである
   - 1件目のカテゴリ（カードのバッジと同じもの）が「イベント」である
   - `eventDate` を日付として解釈できる
3. 開催日ラベルがあるカードでは、公開日に「公開」を付けて区別する（例の「公開：」「開催：」に従った。ラベルの無いカードは従来どおり日付のみ）
4. `eventDate` の解釈は `/events/` と同じ3形式（単日・`A/B` の期間・YAML 配列）。`eventEndDate` があれば期間の終了日に使う（`/events/` と同じ）
5. 解釈できない値・実在しない日付・終了日が開始日より前の期間・3区切り以上の値には、**何も出さない**（生の文字列を出さない）
6. 開催日の年は公開日と同じ年なら省略する。期間の終了日は開始日と同じ年なら省略する
7. 公開日の値・記事の並び順・frontmatter（`date`・`lastmod`・`eventDate`）には一切関与しない

お知らせ・スポーツ・開店・閉店などの `eventDate`（告知の対象日・試合日・開店日など）は、意味が「開催日」と断定できないため、ラベルを出さず公開日だけにした。

## 第7章 未解決事項と工程1aへの引き継ぎ

### 7.1 eventDate の意味の整理

- `eventDate` を持つ ja posts 361 記事のうち、イベントは 138 記事だけ。残りはスポーツ 74（試合日）・開店・閉店 64（開店日・閉店日）・グルメ・カフェ 31（期間限定メニュー等）・お知らせ 30（制度開始日・告知の対象日）・子育て・教育 20・ニュース 4
- 工程1b では「1件目のカテゴリがイベント」の記事だけを開催日として扱った。スポーツの試合日なども本来は「実施日」として見せる価値があるが、意味が混在したまま一律に「開催」と出すと誤表示になるため見送った
- **工程1a での推奨**: 意味ごとの項目を分ける（例: イベント＝`eventDate`、試合＝`matchDate`、開店・閉店＝`shopStatus`＋日付、お知らせ＝`noticeDate`）か、`eventDate` に種別を添える。`card-dates.html` は「どの項目を、どのラベルで出すか」を1か所で決める作りにしてあるので、項目が決まればラベルの追加はこの partial だけで済む
- カテゴリが2つある記事: 2本のスポーツ記事が2件目に「イベント」を持つ。工程1b はバッジと同じ1件目で判定したため、開催日ラベルは出ていない。一方、終了通知（`event-ended-notice.html`）は「どこかにイベントがあるか」で判定しているため、判定基準がそろっていない
- `eventDate` の値に実在しない日付（例: 2月30日）が入ると、`/events/` と終了通知の `time` 関数でビルドが止まる（カードは安全に省略する）。検証ルール（`post-rules.js` の `EVENTDATE_FORMAT`、工程0.5 で追加）は形式と実在性を検査しているが**警告扱い**で投稿を止めない。また期間の逆順（終了日が開始日より前）と3区切り以上は検出しない。工程1a でエラーへの格上げと検査の追加を推奨

### 7.2 開店・閉店年表の分類体系

指示どおり変更していない。工程0 C-2-a の誤分類（「一時休業」→閉店、「臨時休業」「営業再開」→リニューアル、「出店予定か」→オープン）は残っている。正規表現の順序だけを入れ替えると「休業から再開」等で別の誤分類が出るため、種別語彙（open / open_planned / close / temp_close / reopen / renewal / move / feature 等）を決めてから、`openclose.yaml` と記事 frontmatter の側で直すことを推奨する。

### 7.3 イベントカレンダーの掲載基準

変更していない。カレンダーと Event 構造化データは今も「`eventDate` があれば、カテゴリを問わず掲載」で、イベント以外の ja posts 223 記事が載っている（工程0 F-3・F-4）。工程1b で決めた「1件目のカテゴリがイベント」の基準を、工程1a・5 でカレンダーと Event 構造化データにも適用するかを判断してほしい（適用するとカレンダーの件数と Event 出力ページが減る）。

- 推奨: イベント記事は `eventDates` も読み、2〜3日なら「10月25日(日)・11月3日(火)」、それ以上は「10月25日(日)ほか全N日」。変更は `layouts/partials/card-dates.html` の1か所で済む。記事側の個別修正はしない

**(3) イベントカレンダーへの掲載基準**

- 現状: `eventDate` があればカテゴリを問わず掲載（イベント以外 224 記事が載る）。一方、`eventDates` だけのイベント 55 本は載らない。配列は初日〜最終日の連続期間として表示され、飛び石の日程が「10/25〜11/3」のように誤って見える
- 推奨: 掲載はイベントカテゴリ（または明示の項目）に限定し、飛び石の日程は日付ごとの行にする。工程5（カレンダー改修）の前提として工程1a で決める

**(4) Event 構造化データとの整合性**

- 現状: カレンダーと同じく `eventDate` があれば全カテゴリで Event を出力し、配列は開始日〜終了日の連続期間として出力。`eventDates` だけの記事は出力しない。主催者・会場の既定値「浦安市」も残る（工程0 P05）
- 推奨: 掲載基準をカレンダーとそろえる。飛び石の日程は日付ごとの Event か `eventSchedule`。主催者・会場は値がある場合だけ出力する

**(5) 日付入力時の検証ルール**

- 推奨: `eventDate`・`eventDates` の形式と実在性をエラーにする。逆順の期間・3区切り以上・`eventDate` と `eventDates` の併用・イベント以外のカテゴリでの `eventDate` を警告にする。投稿ツール（`post-rules.js`）と CI（`validate-content.mjs`）は同じルールを共有しているので、1か所の変更で両方に効く。記事化プロンプトにも同じ定義を反映する
