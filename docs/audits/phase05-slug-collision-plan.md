## 0. 判断の基準

| 原則 | 内容 |
|---|---|
| 原則1 | 現在公開中の記事の URL と表示内容は変えない |
| 原則2 | 旧記事にしかない具体的な情報（料金・時刻・出演者など）があるなら、旧記事に**新しい slug を付けて復活**させる。現行 URL はそのまま |
| 原則3 | 旧記事の情報が現行記事にすべて含まれるなら**統合**（旧ファイルを削除。URL と表示は変わらない） |
| 原則4 | タイトルが同一の組を両方公開すると検索で競合するため、復活させる場合はタイトルの区別（「（第1報）」等）も必要 |

**既存の前例**: 2026-06-13 の `490c9644`（D-Rocks 市長訪問）で、旧記事に新 slug（`…-preview-2026`）を付けて衝突を解消している。本書の「復活」はこの方式と同じ。

**新 slug の命名案**: `<現 slug>-<ファイル名の日付 YYYYMMDD>`（例: `aloha-urayasu-2026-20260914`）。機械的に一意になり、どの記事か分かる。

**「旧情報だけの事実」の判定方法**: 本文と description から数値・時刻・金額・固有名詞を抜き出し、現行記事に無いものを列挙した（機械抽出。言い換えは拾えないため、最終確認は人が行う）。

### T02・T03 タグの表記ゆれ <a id="t02"></a><a id="t03"></a>
- 同じ URL になる別表記のタグがあり、表題（と記事数に依存する index／noindex）がビルドごとに入れ替わる。例: `/tags/ブリオベッカ浦安市川/` は2回のビルドで `index, follow` と `noindex, follow` が入れ替わった
- **推奨**: posts の tags を一方の表記に統一（記事の frontmatter の書き換えになるため承認が必要）。lastmod の更新要否もあわせて判断が必要（本文は変わらないため不要とする案）

## 3. 承認後の作業手順（共通）

1. 本書の推奨（または代替案）を ID ごとに決める
2. 復活: 旧ファイルの `slug:` を新 slug に変更し `lastmod` を付ける（CLAUDE.md）。必要なら本文冒頭に続報の関係を明記
3. 統合: 固有情報を現行記事へ移す（`lastmod` 更新）→ 旧ファイルを削除
4. `scripts/validate/known-issues.json` から該当 ID の行を削除（CI が「解消済み」と表示するので、その一覧どおりに消す）
5. `hugo --printPathWarnings` で重複出力パスが消えたこと、`node scripts/baseline/compare.mjs` で意図した URL 以外が変わっていないことを確認
